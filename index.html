Why 100% Local?

Every certificate operation in this toolkit runs entirely inside your browser. Nothing is ever sent to a server.

TL;DR

  • ✓Your certificate files, private keys, and passwords never leave your device — there is no backend server receiving them.
  • ✓All cryptographic operations (decryption, parsing, conversion) are performed by OpenSSL running directly in your browser tab.
  • ✓The Memory Vault exists only in your browser’s RAM for the current session — nothing is written to disk or localStorage.
  • ✓You can download the page and run it completely offline — once the assets are loaded, no network connection is needed.

What is WebAssembly?

WebAssembly (WASM) is a low-level binary instruction format that runs inside the browser at near-native speed. Every modern browser (Chrome, Firefox, Safari, Edge) includes a sandboxed WASM runtime as part of the JavaScript engine. Code compiled to WASM has no direct access to the operating system, the file system, or the network — it can only interact with what the JavaScript host explicitly provides to it.

This means a WASM module cannot exfiltrate data even if it wanted to: the sandbox physically prevents it from opening sockets or reading files outside the controlled API surface.

OpenSSL compiled to WASM

OpenSSL is the industry-standard C library used by servers worldwide for TLS, certificate management, and cryptographic operations. Using Emscripten (a C/C++ to WebAssembly compiler toolchain), the OpenSSL source is compiled into a openssl.wasm binary and a thin JavaScript glue layer (openssl.js).

The result is the exact same OpenSSL you would invoke from a terminal — openssl x509, openssl pkcs12, openssl pkey — executing inside a browser tab instead of a shell.

How a tool operation works end-to-end

  1. 1Your file or pasted PEM data is read by JavaScript using the browser’s FileReader API — it stays in the tab’s memory.
  2. 2A WASM instance of openssl.wasm is initialised. Each operation typically gets its own isolated instance to avoid state bleed.
  3. 3The file bytes are written into the WASM module’s linear memory (a private, sandboxed block of bytes — like RAM for the module). The OpenSSL command is then executed inside that memory space.
  4. 4OpenSSL writes its output (the parsed certificate fields, the converted file bytes, the extracted key) back to the same linear memory.
  5. 5JavaScript reads the result out and renders it in the UI or offers it as a download via a temporary Blob URL. The WASM instance is then discarded.

At no point in this flow is there a fetch() or XMLHttpRequest carrying your data. You can verify this yourself by opening DevTools → Network and filtering by XHR/Fetch while using any tool.

Memory Vault & session scope

The Memory Vault is a plain JavaScript array held in the page’s runtime memory. It is never written to localStorage, sessionStorage, IndexedDB, or cookies. Closing or refreshing the tab immediately discards all vault contents. This is intentional — private keys should not persist beyond the session you need them.

You can audit the full source at any time — open DevTools and inspect js/.
